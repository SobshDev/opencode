Tools allow the LLM to perform actions in your codebase. OpenCode comes with a set of built-in tools, but you can extend it with [custom tools](/docs/custom-tools) or [MCP servers](/docs/mcp-servers).

By default, all tools are **enabled** and don't need permission to run. You can control tool behavior through [permissions](/docs/permissions).

---

## Configure

Use the `permission` field to control tool behavior. You can allow, deny, or require approval for each tool.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "deny",
    "bash": "ask",
    "webfetch": "allow"
  }
}
```

You can also use wildcards to control multiple tools at once. For example, to require approval for all tools from an MCP server:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "mymcp_*": "ask"
  }
}
```

[Learn more](/docs/permissions) about configuring permissions.

## Built-in

Here are all the built-in tools available in OpenCode.

---

### bash

Execute shell commands in your project environment.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "bash": "allow"
  }
}
```

This tool allows the LLM to run terminal commands like `npm install`, `git status`, or any other shell command.

---

### edit

Modify existing files using exact string replacements.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "allow"
  }
}
```

This tool performs precise edits to files by replacing exact text matches. It's the primary way the LLM modifies code.

---

### write

Create new files or overwrite existing ones.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "allow"
  }
}
```

Use this to allow the LLM to create new files. It will overwrite existing files if they already exist.

:::note
The `write` tool is controlled by the `edit` permission, which covers all file modifications (`edit`, `write`, `apply_patch`).
:::

---

### read

Read file contents from your codebase.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "read": "allow"
  }
}
```

This tool reads files and returns their contents. It supports reading specific line ranges for large files.

### grep

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "grep": "allow"
  }
}
```

Fast content search across your codebase. Supports full regex syntax and file pattern filtering.

---

### glob

Find files by pattern matching.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "glob": "allow"
  }
}
```

Search for files using glob patterns like `**/*.js` or `src/**/*.ts`. Returns matching file paths sorted by modification time.

### lsp (experimental)

Interact with your configured LSP servers to get code intelligence features like definitions, references, hover info, and call hierarchy.

:::note
This tool is only available when `OPENCODE_EXPERIMENTAL_LSP_TOOL=true` (or `OPENCODE_EXPERIMENTAL=true`).
:::

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "lsp": "allow"
  }
}
```

Supported operations include `goToDefinition`, `findReferences`, `hover`, `documentSymbol`, `workspaceSymbol`, `goToImplementation`, `prepareCallHierarchy`, `incomingCalls`, and `outgoingCalls`.

To configure which LSP servers are available for your project, see [LSP Servers](/docs/lsp).

### apply_patch

Apply patches to files.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "edit": "allow"
  }
}
```

This tool applies patch files to your codebase. Useful for applying diffs and patches from various sources.

When handling `tool.execute.before` or `tool.execute.after` hooks, check `input.tool === "apply_patch"` (not `"patch"`).

`apply_patch` uses `output.args.patchText` instead of `output.args.filePath`. Paths are embedded in marker lines within `patchText` and are relative to the project root (for example: `*** Add File: src/new-file.ts`, `*** Update File: src/existing.ts`, `*** Move to: src/renamed.ts`, `*** Delete File: src/obsolete.ts`).

:::note
The `apply_patch` tool is controlled by the `edit` permission, which covers all file modifications (`edit`, `write`, `apply_patch`).
:::

### websearch

Search the web for information.

:::note
This tool is only available when using the OpenCode provider or when the `OPENCODE_ENABLE_EXA` environment variable is set to any truthy value (e.g., `true` or `1`).

To enable when launching OpenCode:

```bash
OPENCODE_ENABLE_EXA=1 opencode
```

:::

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "websearch": "allow"
  }
}
```

Performs web searches using Exa AI to find relevant information online. Useful for researching topics, finding current events, or gathering information beyond the training data cutoff.

No API key is required — the tool connects directly to Exa AI's hosted MCP service without authentication.

:::tip
Use `websearch` when you need to find information (discovery), and `webfetch` when you need to retrieve content from a specific URL (retrieval).
:::

### question

Ask the user questions during execution.

```json title="opencode.json" {4}
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "question": "allow"
  }
}
```

This tool allows the LLM to ask the user questions during a task. It's useful for:

- Gathering user preferences or requirements
- Clarifying ambiguous instructions
- Getting decisions on implementation choices
- Offering choices about what direction to take

Each question includes a header, the question text, and a list of options. Users can select from the provided options or type a custom answer. When there are multiple questions, users can navigate between them before submitting all answers.

### models

Search the models that the current session can call with [`model_call`](#model_call).

All fields are optional:

| Field        | Type      | Description                                                                                  |
| ------------ | --------- | -------------------------------------------------------------------------------------------- |
| `query`      | string    | Search provider IDs, model IDs, display names, families, and variant names.                  |
| `providerID` | string    | Return only models from this exact provider.                                                 |
| `tools`      | boolean   | Filter by whether the target model supports tool calls.                                      |
| `limit`      | integer   | Number of results to return. Defaults to `20` and cannot exceed `50`.                         |
| `cursor`     | string    | Continue a search using the exact `nextCursor` returned by the previous call.                 |

For example:

```json
{
  "query": "codex",
  "providerID": "openai",
  "tools": true,
  "limit": 20
}
```

Results are deterministic and paginated. Each item contains a canonical structured model reference and its available variants:

```json
{
  "ref": {
    "providerID": "openai",
    "id": "gpt-5.1-codex"
  },
  "variants": ["high"]
}
```

Copy the `ref` returned by `models` into `model_call`. To request a variant, add one of that same item's `variants` to the copied reference; do not combine a provider ID, model ID, and variant from different results.

The result contains only connected, enabled, text-capable models that OpenCode can resolve in the current runtime. It exposes display and family names, variants, capabilities, context and output limits, status, and cost. Provider URLs, credentials, headers, request bodies, and provider settings are never returned.

:::note
This is a model-facing discovery tool. The terminal commands [`opencode models`](/docs/cli#models) and [`/models`](/docs/tui#models) remain available for listing and selecting models.
:::

### model_call

Delegate a prompt to an exact model in a fresh child session.

```json
{
  "model": {
    "providerID": "openai",
    "id": "gpt-5.1-codex",
    "variant": "high"
  },
  "prompt": "Review the current diff. Report correctness, security, and test gaps with file and line references.",
  "background": false
}
```

`model.providerID` and `model.id` are required. `model.variant` is optional. Selection is exact: OpenCode never fuzzy-selects a model or silently falls back to another one. Use [`models`](#models) first when the reference is not already known.

`prompt` is required. `background` defaults to `false`. You can also provide `output_schema` with an object-root JSON Schema when the caller needs structured data:

```json
{
  "model": {
    "providerID": "anthropic",
    "id": "claude-sonnet-4-5-20250929"
  },
  "prompt": "Review the current diff and return the findings.",
  "output_schema": {
    "type": "object",
    "properties": {
      "findings": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "severity": { "type": "string" },
            "summary": { "type": "string" }
          },
          "required": ["severity", "summary"],
          "additionalProperties": false
        }
      }
    },
    "required": ["findings"],
    "additionalProperties": false
  }
}
```

OpenCode validates structured output. If a model does not support native structured output, OpenCode requests JSON and can make one corrective child turn before returning a validation failure.

#### Child context

Every call creates a new child session. It uses the caller's selected agent, system context, tools, permission overlay, step policy, Location, and workspace; only the model changes. The parent transcript and generated summaries are not copied into the child, so include everything the target needs in `prompt`.

The child and parent use the same live workspace. Changes made by either session are immediately visible to the other, and the called model may edit files when its inherited tools and permissions allow it.

:::caution
Independent model review does not imply a read-only or isolated workspace. Ask the child only to review, or configure suitable edit and shell permissions, when it must not change files.
:::

Model calls may be nested to depth `2`; an attempt to create a depth-`3` child is rejected. A session can have at most 20 active direct model-call children at once. Calling the same model more than once is allowed, but each invocation still receives a fresh session.

Only a tool-capable model can invoke `model_call`. A connected text-capable model without tool support can still be a target.

#### Foreground review

A foreground call waits for the child to finish and returns its ordered final text, structured value when requested, usage and cost, status, and parent/child session IDs. A useful prompt to the parent model is:

```text
Use models to find an available model from a different provider. Call it in the foreground to review the current diff independently, then assess its findings before responding.
```

Interrupting the parent also interrupts and cancels its foreground child. A foreground call can be detached to continue in the background.

#### Parallel independent reviews

The caller can start multiple model calls concurrently. For example, it can issue these two independent foreground calls in parallel:

```json title="Review A"
{
  "model": {
    "providerID": "anthropic",
    "id": "claude-sonnet-4-5-20250929"
  },
  "prompt": "Independently review the current diff. Focus on correctness and edge cases. Do not edit files."
}
```

```json title="Review B"
{
  "model": {
    "providerID": "openai",
    "id": "gpt-5.1-codex",
    "variant": "high"
  },
  "prompt": "Independently review the current diff. Focus on security and missing tests. Do not edit files."
}
```

Each reviewer starts without the parent's conversation or the other reviewer's result. After both calls settle, the parent can compare their findings.

#### Background delegation

Set `background` to `true` when the parent should keep working:

```json
{
  "model": {
    "providerID": "openai",
    "id": "gpt-5.1-codex"
  },
  "prompt": "Investigate the flaky integration test, implement a focused fix, and run the relevant tests.",
  "background": true
}
```

The tool returns immediately with the call ID, child session ID, actual model, and current status. Interrupting the parent does not cancel a background child. When the child settles, OpenCode delivers its result exactly once to the parent at the next safe conversation boundary and wakes an idle parent. The terminal child-session card can be used to inspect, navigate to, or cancel the work.

The `model_call` permission controls whether a model may delegate:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "model_call": "ask"
  }
}
```

:::note
`model_call` does not replace the `task` tool. `task` continues to invoke configured, named [subagents](/docs/agents/#subagents) with their own agent profiles; use `model_call` when the target is an exact model reference.
:::

## Internals

Internally, tools like `grep` and `glob` use [ripgrep](https://github.com/BurntSushi/ripgrep) under the hood. By default, ripgrep respects `.gitignore` patterns, which means files and directories listed in your `.gitignore` will be excluded from searches and listings.

---

### Ignore patterns

To include files that would normally be ignored, create a `.ignore` file in your project root. This file can explicitly allow certain paths.

```text title=".ignore"
!node_modules/
!dist/
!build/
```

For example, this `.ignore` file allows ripgrep to search within `node_modules/`, `dist/`, and `build/` directories even if they're listed in `.gitignore`.
